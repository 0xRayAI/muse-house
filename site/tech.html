How it's built

An MCP service, stateless by design.

For the technically curious. Everyone else: here's how it works.

The shape of it

Muse House is an external MCP (Model Context Protocol) service, consumed through a custom Muse connector. It speaks Streamable HTTP on a single /mcp endpoint and answers every request with one plain JSON body — no Server-Sent Events, no sessions, no streaming. Boring on purpose: it's the most compatible shape for review pipelines and egress proxies.

The endpoint

POST https://mymuse.house/mcp · GET https://mymuse.house/health

No authentication on the public blueprint MCP tier. No accounts, no login walls for blueprints. Token-protected website routes only: GET /api/bling/orders (BLING_API_TOKEN) and POST /api/bling/dev/grant (BLING_DEV_TOKEN). No connector OAuth is invented for blueprints.

Ten tools · nine rooms

Rooms in data/rooms.json: Art, Bling, Coach, Dev, Game, Health, Home, Money, Travel.

Blueprints [read]: suggest_utilities ranks which Muse connectors a household should turn on. suggest_steps builds the operating plan (returns the plan only). list_rooms and get_room_brief serve the nine room blueprints. get_house_template mints starter HOUSE.md / OP-PROC.md. stamp_rooms returns the executable room-creation protocol — the MCP tool does not create chats; the host executes. check_room_updates compares a house's recorded room versions against the live blueprints and returns patch-or-restamp guidance.

Governance [read]: codex_check runs a planned action against the 22-term consumer codex — advisory, not a gate.

Feedback: get_feedback_form [read] serves the form schema; send_feedback [sensitive-write] relays structured, user-confirmed feedback to the team inbox via durable offsite email (personal data redacted server-side; rate-limited; nothing stored).

Bling money posture: purchases are website Stripe Checkout only (/bling.html). Cards stay on Stripe. Bling is not an MCP money-movement tool — no transfers, trades, or payments via MCP. No Meta money tools.

Stateless means stateless

The service stores nothing: no user data, no conversation history, no identifiers. Tool arguments are not persisted. Your board, routines, approvals, and connected accounts live inside your own Muse — never here. Feedback messages are forwarded to the support inbox and forgotten; only anonymous rate-limit counters exist, in memory, never on disk. The privacy policy says the same thing at greater length.

Open source

The whole thing is public: 0xRayAI/muse-house (MIT). Run it yourself with node src/server.mjs — the Dockerfile is in the repo. Machine-readable docs live at llms.txt.
